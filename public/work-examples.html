AI agents · MTDCNC · 2025 to 2026

An inbox that turns itself into a task list

Two agents built in Claude Code and Python. One reads a mailbox and keeps the task board in step with it. The other runs tools when someone tags it on the board.

  • Claude Code
  • Python
  • Monday.com API
  • Spend ledger

The problem

Requests arrive by email from colleagues, clients and suppliers, mixed in with notifications and promotions. The work itself is tracked on a Monday.com board. Keeping the board in step with the inbox was manual work.

What I built

  • An agent that reads the inbox and sent items since its last run, discards notifications, promotions and junk, and extracts the real tasks.
  • Each task is checked against the open items on the board. New ones are added with a note of the source email. Existing ones have their status moved when the mail shows they have progressed.
  • Where it can do the groundwork alone it does: it looks things up, drafts the reply or the report, and posts what it found on the item.
  • At 07:00 it posts a brief, grouped by whose move each task is and ordered by deadline.
  • A second agent watches the board. Tag it on an item and it runs the right tool, writes the result back and mentions whoever asked. Items are closed on evidence, not on say-so.

How it is controlled

  • A daily spend cap of a few pounds, enforced by a ledger, with a canary run before any batch and a stop switch that halts it at once.
  • It prepares and never sends. Emails and messages wait as drafts until a named person releases them.
  • Steps that do not need judgement are plain Python. The model is called only where reading and deciding are the job.

Where it is now

In daily use. The rules it follows are written down in the repository, so a change in how the team works is a change to a text file, not a rebuild.

  1. MailboxInbox and sent items since the last run
  2. FilterNotifications, promotions and junk removed
  3. ExtractReal tasks pulled out, under the spend cap
  4. DeduplicateMatched against open items on the task board
  5. WriteNew items with a source note, status updates, groundwork posted
  6. Human releaseDrafts wait for a named person before anything is sent
  7. 07:00 briefGrouped by whose move, in deadline order

Publishing · MTDCNC · 2026

A magazine PDF becomes a set of web posts

A Python tool that takes each issue of a bi-monthly magazine and publishes its articles to the website through the WordPress REST API.

  • Python
  • PDF parsing
  • WordPress REST API
  • Image processing

The problem

The magazine is laid out for print and delivered as a PDF. Every article of a page or more also belongs on the website as its own post, with its images, its category and the right company as author. By hand that is copy, paste and re-export, article by article, every issue.

What I built

  • A tool that reads the issue PDF and splits it into articles.
  • It extracts the text and the images, takes the category from the page label and sets the company as the author.
  • It writes a preview folder first, one file per article, so the result can be checked before anything is posted.
  • On approval it creates the posts through the WordPress REST API, with images placed inline where the page had them.
  • A companion tool draws the mock-up images of each new issue from scratch for the website and email.

How it is controlled

  • Nothing is uploaded until the previews have been looked at.
  • I built it with AI-assisted development, but it runs as plain Python with no model calls. An issue costs nothing to process and the output is the same every time.

Where it is now

Used for every issue.

  1. Issue PDFThe print layout, as supplied
  2. SplitArticles of a page or longer identified
  3. ExtractText, images, category from the page label, author company
  4. PreviewOne file per article, checked by a person
  5. PublishPosts created through the WordPress REST API, images inline

Data · MTDCNC

Keeping 120,000 CRM records clean

Python tooling that stops bad data getting into the CRM, takes the bots out of campaign statistics and reports straight from the production database.

  • Python
  • pandas
  • rapidfuzz
  • MySQL
  • SQLite
  • Excel output

The problem

Contact lists arrive from events, clients and two separate platforms. Imported as they come, they create duplicates and mismatched companies. Meanwhile security scanners and mail privacy proxies click every link in an email, so raw open and click figures overstate real interest.

What I built

  • Import validator. Each incoming record runs down a resolution chain: email, exact name, company domain, then fuzzy name matching. Matches of 90% or more are approved automatically. Matches of 75 to 89% go to a review workbook, along with any record whose country does not agree with the one on file.
  • Bot-click filter. Classifies each click using Apple Mail Privacy Protection address ranges, an IP classification cache held in SQLite and behavioural scoring, so reports show people and not scanners.
  • Campaign reports. A script reads the email platform's production database and writes the customer report in Excel: summary, opens and clicks.
  • Master list. In October 2026 I merged the contact bases of two systems into one deduplicated master list of 121,663 contacts.

How it is controlled

  • Reporting connects to the production database read-only.
  • Any write follows plan, apply, verify: the script shows what it will change, makes the change, then reads it back.
  • Uncertain matches are never guessed. They go to a person in a workbook built for quick review.
  1. Incoming recordFrom an event list, a client or another platform
  2. Email matchExact match on address
  3. Name matchExact match on name
  4. Domain matchCompany domain against known accounts
  5. Fuzzy match90% and over approved automatically
  6. Review workbook75 to 89% matches and country mismatches, decided by a person
  7. Clean importOnly resolved records reach the CRM

Media operations · MTDCNC · 2026

A video-edit pipeline that runs unattended

A dispatcher that takes edit jobs from a queue, drives Adobe Premiere to build them, and calls for help when a machine misbehaves.

  • Python
  • Claude Code
  • Premiere XML
  • QNAP
  • Pushover

The problem

First assemblies of interview and factory-tour films follow consistent house rules, but building them is repetitive work that has to happen before the creative work starts. An automated build has to survive the things that go wrong on a real workstation: a hidden dialog, a full disk, a network share that drops.

What I built

  • A dispatcher that picks up jobs from a queue, restores any archived material, opens Premiere itself and builds the sequences from XML.
  • The build follows the house cutting rules: minimum shot lengths, where a cut may fall, how supporting footage and captions are laid.
  • The deliverable is a real Premiere project. An editor opens it and carries on, rather than receiving a flat export.
  • Idle jobs are moved to network storage to keep the local disk clear, and restored automatically before a run.
  • On a machine fault the job is held, not lost, and the operator is paged by push notification.

How it is controlled

  • Hold, pause and resume never consume the original request, so a fault costs time and not work.
  • Source footage is never moved or deleted by the tool. Archiving moves working files only.
  • Quality-control renders are checked automatically. Anything for a person to judge waits for that person.

Where it is now

Handed over to a permanent runner machine with a written operations plan and a fault-recovery procedure.

  1. Job queueEdit requests waiting to be built
  2. RestoreArchived material brought back from network storage
  3. BuildPremiere opened, sequences built from XML to the house rules
  4. CheckQuality-control renders tested automatically
  5. EditorOpens the project and finishes the film
  6. ArchiveIdle jobs moved to network storage

On a machine fault the job is held and the operator is paged.

Email at a million a month, built to a rule set

The sending infrastructure, the authentication behind it and the build standard that keeps campaigns rendering correctly in Outlook.

  • SPF
  • DKIM
  • DMARC
  • SendGrid
  • Mailwizz
  • HTML / VML
  • Python linter

The problem

A media business sends on behalf of many clients across several brands and domains. Volume peaked at around a million emails a month. At that scale a deliverability problem or a broken layout in Outlook is a commercial problem.

What I built and run

  • Sending through SendGrid and Mailwizz, with SPF, DKIM and DMARC maintained across the sending domains, plus reputation monitoring and suppression management.
  • More than 3,000 hand-coded HTML and VML campaigns over ten years.
  • A written rendering rule set covering Outlook's VML, DPI scaling and dark mode, and a linter that every build has to pass before it can be proofed.
  • A Python pipeline from Photoshop design to HTML, and a converter that brings supplied or AI-generated HTML up to the house standard.
  • A deliverability tracker that follows authentication and reputation per brand.

How it is controlled

  • Builds are rendered at desktop and phone width and linted before a person sees a proof.
  • Test sends go to test lists. Live campaigns are prepared as drafts and sent by a person.

  3. LintAutomated checks: links, images, Outlook rules

Infrastructure · MTDCNC

Global video ingest, proxy and archive

A self-hosted system that lets around 20 editors in the UK, Europe, the USA, Mexico and India work on the same footage, with about 100 TB archived for roughly £100 a month.

  • QNAP
  • Dropbox
  • AWS S3 Glacier
  • HandBrake
  • 10 Gb network

The problem

Video files were spread across individual editing workstations, posted physical media and dozens of consumer external drives. There was no central archive, no reliable backup and no practical way to find old footage.

Research and cost

I reviewed commercial media-management platforms, bespoke vendor proposals and enterprise storage. The off-the-shelf systems were quoted in the tens of thousands of pounds a year and still lacked flexible ingest, proxy workflows or ownership of the data.

What I built

  • Two QNAP units of about 100 TB each: one on site, one at a remote location for failover.
  • The primary unit synchronises with Dropbox, so footage can be ingested from anywhere while the office keeps fast local access over a 10 Gb network and a 1 Gb leased line.
  • An automated batch process checks for new files every hour and generates proxy media at about 5% of the original size, so remote editors can start on a slow connection while full-resolution files follow.
  • Nightly replication to the second unit, and a nightly long-term archive to Amazon S3 Glacier.

Result

Delivered for about £7,000 of capital spend with no software licences. Running costs are around £100 a month for Glacier and £216 a year for Dropbox. Any project can be opened by any editor, anywhere, and the business no longer depends on drives in the post.

Personal project · 2025 to 2026

This site, and the chatbot on it

A static site with a small serverless backend and a retrieval chatbot that is only allowed to answer from records I wrote.

  • Cloudflare Pages
  • Workers
  • Vectorize
  • OpenAI API
  • Postmark
  • HTML / CSS / JS

What it is

  • Plain HTML, CSS and JavaScript with no framework and no build step, deployed from GitHub to Cloudflare Pages.
  • A Cloudflare Worker behind /api that handles the chatbot and the contact form.
  • A curated library of short records about my roles, projects and tools, embedded and stored in Cloudflare Vectorize.
  • For each question the Worker retrieves the closest records and asks the model to answer from those alone. If the library does not cover it, the chatbot says so.

How it is controlled

  • The chatbot is told what it may not claim, including the limits of my experience with tools I have only touched.
  • Writing to the library needs a secret key, and questions are rate-limited and capped per day.

  1. QuestionTyped into the widget on any page
  2. EmbedTurned into a vector
  3. RetrieveClosest records fetched from the library
  4. AnswerModel answers from those records only
  5. Not covered?It says so and offers the contact form
